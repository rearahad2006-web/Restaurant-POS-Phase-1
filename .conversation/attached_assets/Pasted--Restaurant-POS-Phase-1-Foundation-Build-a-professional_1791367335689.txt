# Restaurant POS — Phase 1 Foundation

Build a professional restaurant POS system for a small family-owned restaurant.

IMPORTANT:
This is the FIRST development phase. Do not try to build every possible restaurant feature. Build a clean, working foundation that we can test and expand in later phases.

The application will initially be developed/tested in Replit, but it MUST be designed so that later we can move it to a Windows 10 PC and run it locally at the restaurant.

## Restaurant Information

Current setup:

- One POS computer
- Windows 10
- Approximately 10 menu items initially
- Tables must be dynamically manageable
- Start with 1 table, but the manager must be able to add, edit, and remove tables later
- Order types:
  1. Dine-in
  2. Takeaway
  3. Delivery
- No kitchen display system in Phase 1
- No KOT system in Phase 1
- No inventory system in Phase 1
- Payment methods:
  - Cash
  - Card
  - Easypaisa
  - JazzCash
  - Other
- A thermal receipt printer will be added later
- Receipt printing MUST be considered from the beginning so the architecture can support physical Windows printer printing later.

## Core Goal

Create a simple, fast, professional restaurant POS.

The main workflow must be:

Dine-in:
Select table → Add items → Cart → Checkout → Payment → Receipt → Complete order

Takeaway:
Takeaway → Add items → Checkout → Payment → Receipt → Complete order

Delivery:
Delivery → Customer information → Add items → Delivery charge → Checkout → Payment → Receipt → Complete order

## Technology

Use a simple, maintainable technology stack.

Preferred:

- React
- TypeScript
- Vite
- Tailwind CSS
- SQLite-compatible/local-first data architecture

Do NOT make the application dependent on Replit-specific databases or services.

Avoid unnecessary cloud services.

The code must be portable and easy to run outside Replit later.

If SQLite cannot be used directly in the current Replit browser environment, create a clean database abstraction/repository layer so SQLite can be connected later without rewriting the application's business logic.

Do not use a complicated microservice architecture.

Keep the project simple.

## Data Architecture

Create clear data models for:

- User
- RestaurantSettings
- Table
- Category
- MenuItem
- Order
- OrderItem
- Payment

Use IDs and timestamps.

Orders must preserve their items and prices at the time of purchase.

IMPORTANT:
If a menu item's price changes later, old orders must NOT change.

Use a repository/data-access layer instead of putting database logic directly inside React components.

The architecture should make it easy to replace the temporary development storage with SQLite later.

## Local-First Requirements

This is extremely important.

The final application is intended to run on one Windows 10 restaurant computer.

Therefore:

- Core POS functionality must not require internet.
- Do not depend on Replit authentication.
- Do not depend on Replit database.
- Do not depend on cloud APIs for basic billing.
- Restaurant data should be locally stored.
- Keep database access isolated.
- Keep printing isolated.
- Keep business logic independent of Replit.
- Do not hard-code Replit URLs.
- Do not hard-code the current development environment.

If temporary browser storage is required during this first Replit phase, isolate it behind a repository interface so it can later be replaced by SQLite.

## UI Design

Make the UI professional and suitable for a restaurant cashier.

Requirements:

- Fast navigation
- Large buttons
- Easy-to-read prices
- Clear cart
- Responsive desktop layout
- Clean modern design
- Minimal unnecessary animations
- Good contrast
- Keyboard-friendly where practical

This is primarily a desktop application, so optimize for a Windows 10 desktop screen rather than mobile.

Use a consistent restaurant POS design.

## Error Handling

Add basic validation.

Examples:

- Cannot checkout an empty cart.
- Price must be valid.
- Quantity must be at least 1.
- Delivery order should require customer information.
- Cannot delete a table that currently has an active order without warning.
- Cannot complete payment if required information is missing.

Show clear user-friendly error messages.
